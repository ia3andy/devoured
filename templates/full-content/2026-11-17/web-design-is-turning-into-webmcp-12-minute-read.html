On September 28, Shopify extended WebMCP into checkout. Around the same time, Gil Greenberg, who works on agentic commerce at Shopify, shared a benchmark that explains the whole year. He ran ten checkout tasks across two test shops, six times each, with the same OpenAI model and the same prompts. When the agent worked the checkout the way a person does, reading the page and clicking through it, it finished 56 of 60 attempts at 27.4 seconds apiece, not counting page setup. When it called the tools the checkout page registers through WebMCP, it finished all 60, at 10.3 seconds apiece and 58 percent less in model fees at OpenAI’s list prices.

Nobody looked at the page during the second run. Somebody designed it anyway.

It’s Shopify’s test on Shopify’s shops, so discount the decimals. The direction isn’t in dispute. On August 5, Shopify announced that every Liquid storefront would register ten WebMCP tools in the browser, effective August 21, with names like search_catalog and update_cart and nothing for the merchant to install or configure. The next day, Cloudflare released a developer preview that injects a WebMCP bridge into a site’s HTML at the edge, switched on from the dashboard with no change to the origin. On August 25, OpenAI turned on WebMCP in the ChatGPT desktop app’s built-in browser, called it “site tools,” and opened a ten-day hackathon with Chrome, Cloudflare, Shopify, Vercel, Netlify and Render as partners.

The traffic had already flipped. On June 3, Cloudflare CEO Matthew Prince posted that automated traffic had overtaken human traffic, a first for the internet, with bots making 57.5 percent of HTTP requests for HTML content against 42.5 percent for people. “Welp, that happened faster than I predicted.” At SXSW in March he had put the crossover in 2027.

The industry reads all of this one of two ways, and both reads are lazy. The marketing read says WebMCP is the new SEO, so register a few tools, call the site agent-ready and wait for the traffic. The doom read says the dead internet theory just came true and the web is now bots talking to bots. Neither describes what’s being built. The working part of your website is being rewritten as a list of function names and English descriptions, executed by a model inside your customer’s logged-in session. That’s the redesign. Most of the people paying for it haven’t read it.

Google and Microsoft Wrote It. Everyone With an Agent Wants It.

WebMCP started as two proposals that looked alike. Kyle Pflug, group product manager for the web platform at Microsoft Edge, told The New Stack that Microsoft’s version, WebModel Context, sat in the public Edge explainers repository and that Chrome’s team had drafted something very similar. Patrick Brosset of the Edge team introduced the merged effort on his blog on August 28, 2025, as a joint Edge and Google project. It lives in the W3C’s Web Machine Learning Community Group. The current draft, dated November 10, lists four editors, Brandon Walderman and Samuel Dallstream of Microsoft and Khushal Sagar and Dominic Farolino of Google, and it states that it’s neither a W3C Standard nor on the Standards Track. The two developers who had working versions before either browser did, Alex Nahas with MCP-B and Jason McGhee, are thanked in the acknowledgments.

A page calls document.modelContext.registerTool() with a name, a natural-language description, a JSON schema for the inputs and a JavaScript function to run. An agent in the browser asks the page what it offers. Then it calls the tools instead of guessing which div is the checkout button. Tools can carry hints. The readOnlyHint flag marks a tool that changes nothing, consequentialHint marks one that books a flight or moves money, and untrustedContentHint marks output that somebody else wrote. There’s a declarative version too. Add toolname and tooldescription attributes to an ordinary HTML form, put a toolparamdescription on each field, and the browser builds the tool for you. The early preview hung the whole API off navigator, and the current draft hangs it off document. That’s how settled it is.

Chrome ran its usual play. An early preview went out behind a flag in Chrome 146 Canary on February 10, with Google’s André Cipriani Bandarra promising agents “increased speed, reliability, and precision.” At I/O on May 19, Google said Gemini in Chrome would soon support WebMCP and showed a logo wall of brands experimenting with it, among them Expedia, Booking.com, Credit Karma, TurboTax, Redfin, Etsy, Instacart and Target. The Chrome 149 origin trial opened June 9. Edge is running its own trial in Edge 150, and Brave has experimental support in its Leo assistant. OpenAI’s support lives in the ChatGPT desktop app because OpenAI’s actual browser didn’t make it. Atlas launched in October 2025. OpenAI set its end date for August 9, sixteen days before shipping WebMCP in the app that replaced it.

The two engines that aren’t Chromium are less excited. A Mozilla reviewer proposed a neutral position, Mozilla’s engineers favored the JavaScript API over the declarative one, and the review suggested a more accurate name, Website Tool API, since WebMCP doesn’t use the MCP specification at all. WebKit’s reviewers proposed opposing it. Their argument is that the gaps agents run into belong in HTML and ARIA, the accessibility layer the web already has, and that a parallel tool layer makes it visible when an agent is driving, which lets a site treat agents differently from people. If you build for WebMCP today, you’re building for Chromium and ChatGPT. Safari users get the website.

My bet is that the fight ends with WebMCP as one more HTML attribute on a text box, about as exotic as a data attribute. The declarative draft already hangs a toolparamdescription attribute on each field. WebKit’s lead objection is that this work belongs in HTML and ARIA, and Dominic Farolino, one of Google’s editors on the spec, has already asked WebKit whether it would accept a declarative-only WebMCP. HTML has solved a smaller version of this problem before. The autocomplete attribute tells the browser that a field wants an email address, a street address or a card number, so the browser can fill it in for you, and WebMCP’s declarative half is autofill with a language model behind it. Mozilla’s engineers would rather keep the JavaScript API, so this isn’t settled. But a standard Safari won’t ship isn’t much of a standard, and an attribute is the version every engine can live with. If I’m right, web design turns into WebMCP in the most literal way possible. Whoever builds the form writes a sentence for the model on every field, right next to the label they write for the person.

Screen Scraping Was Slow. Losing the Customer Was Worse.

The official reason everyone wants WebMCP is that agents are terrible at websites. Google’s web.dev guide to agent-friendly sites, by Kasper Kulikowski and Omkar More, describes how an agent perceives a page, through screenshots read by a vision model, through the raw DOM, or through the browser’s accessibility tree. It calls the screenshot route slow and token-expensive, and it says sites built on hover states, shifting layouts and fluid motion are “functionally broken for agents.” Shopify’s 27.4 seconds is that sentence with a stopwatch on it.

The less official reason sits in the explainer’s list of goals, which includes not disintermediating web apps, and the vendors mean it literally. An agent that scrapes your site from a data center doesn’t need your checkout, your brand or the browser it came through. An agent that calls your registered tools inside the user’s own tab keeps all three in the transaction. The current design also requires a visible browsing context and lists headless browsing and fully autonomous agents as non-goals. Shopify’s documentation follows the same logic, telling agent builders to use Checkout WebMCP only when the agent already runs in the buyer’s browser and server-side MCP otherwise, and Shopify says the merchant stays the merchant of record either way. Cloudflare launched its preview with the promise that “creators keep their traffic.” Everyone behind WebMCP has an agent to feed or a toll booth to protect. Google has Gemini in Chrome, which has been browsing for paying US subscribers since January, and Microsoft has Copilot in Edge. OpenAI retired its own browser and now needs you living in its desktop app. Shopify wants agent purchases running through the merchant checkouts it operates, and Cloudflare wants the agent traffic crossing its edge.

None of that makes it a bad idea. We need it for the same reason we needed APIs twenty years ago, because clicking through a UI built for people is the worst integration there is. One declared contract beats every agent vendor’s private scraping heuristics, and the declarative API means a small business can turn the forms it already has into tools without standing up a separate API. What it won’t do is make agents fast. Ten seconds per checkout is fine for a person delegating a purchase and useless for anything that runs in a loop, and Shopify itself recommends server-side MCP for any agent that doesn’t need a browser. If a decision has to happen in milliseconds, the model doesn’t belong in it. Call an API.

The Dead Internet Theory Got the Numbers Right and the Motive Wrong

In January 2021, a user named IlluminatiPirate started a thread on Agora Road’s Macintosh Cafe, a small forum, titled “Dead Internet Theory: Most Of The Internet Is Fake.” The argument was that the internet had died around 2016 or 2017, and that most of what people had seen since was bots and machine-made content, curated by algorithms, with fewer real people every year. The Atlantic wrote it up that year. It stayed in the conspiracy bin until September 2025, when Sam Altman posted that he’d never taken the theory that seriously, but “there are really a lot of LLM-run twitter accounts now.”

The measurements caught up. Imperva’s 2026 Bad Bot Report, the thirteenth edition, put automated traffic at 53 percent of all web traffic in 2025, up from 51 percent the year before, with humans down to 47. HUMAN Security processed more than a quadrillion interactions in 2025 and found that traffic from AI agents and agentic browsers grew 7,851 percent year over year. Then came Prince’s chart. On Decoder, he told Nilay Patel that Cloudflare expects automated traffic to run at about a thousand times the human level in roughly five years.

The numbers deserve a skeptic’s read, and the doom crowd skips it. Cloudflare’s figure is a count of HTTP requests. It says nothing about people or attention. Most of the automation is still crawlers and scripts, and HUMAN’s own breakdown puts training crawlers at 67.5 percent of AI-driven traffic, with agents doing browser-style tasks at 1.7 percent of it in December 2025, after growing nearly eightyfold in a year. PitchBook estimates that about 1 percent of the roughly $20 trillion in work that could plausibly be handed to agents actually goes through them today. Most of the traffic isn’t most of the customers. Yet.

The theory also got the motive wrong. It pictured bots talking to bots for nobody. The fastest-growing bots have a principal, a person who told an agent to book the flight, compare the strollers or finish the checkout, and HUMAN found that 77 percent of agentic interactions happened on product and search pages. Prince told NBC News he thinks the dead-internet reading of his own data is wrong, and on that point he’s right. The internet didn’t die. The humans stopped coming to the door themselves.

What died is the business model that assumed they would. I was employee number six at Break.com in the years when user-generated video was the center of the consumer web, and the entire machine assumed a person on both ends. Somebody uploaded the clip, somebody watched it, and an advertiser paid for the second person’s attention. Every number on the dashboard, from page views to time on site, was a stand-in for a human looking at a screen. Fortune made the same point in July about impressions, funnels and pageview analytics, and quoted Seer Interactive warning that agentic browsers can “inflate engagement, artificially depress bounce rates, and distort session duration.” Prince was more direct. “Bots don’t click on ads.”

In September I argued that content marketing is finished, because the answer engine reads your article so the customer never has to visit. That was about content. WebMCP does the same thing to the rest of the site.

The Page Is Becoming the Receipt

Google’s own guidance shows where design is headed. The web.dev guide calls agents a new type of visitor, then hands you a checklist that asks for real buttons and links instead of styled divs, labels wired to their inputs, layouts that stay put, no controls hidden under transparent overlays, and a pointer cursor on anything clickable. Search Engine Journal noticed that this is the accessibility audit restated. It is. Sites that ignored screen readers for fifteen years are now broken for the visitors that show up ready to buy. One item on Google’s list is to build WebMCP tools, and that’s the part WebKit’s reviewers flagged, warning that agents could end up with richer semantics than screen-reader users get.

WebMCP doesn’t remove the human interface. Its explainer lists replacing human interfaces as a non-goal, a detail the agent-ready consultants tend to skip. It demotes the interface instead. In the declarative flow, by default, the agent fills in the fields, the browser puts focus on the submit button, and the person is asked to check the form and send it. The draft adds two CSS pseudo-classes, :tool-form-active and :tool-submit-active, so a page can restyle itself while an agent is working the form. The designer’s job used to be walking a person down a funnel. Now it’s drawing the screen where a person signs off on what a model already did.

OpenAI’s pitch to developers was that agents would stop guessing, because “you define exactly how they can use your app.” If you sell on Shopify, Shopify defined it. Shopify picked the tools and wrote the descriptions for every Liquid storefront, and as of late September its documentation didn’t say whether a merchant could switch off an individual tool or edit what it says. A merchant can pay an agency for a custom theme, a product shoot and product pages tuned through a dozen A/B tests. The agent sees the same ten functions it sees on every other Liquid store, with a different catalog behind them. Cloudflare goes a step further. Flip the switch and a bridge script gets injected into your HTML at the edge, and your origin code never changes. Your agent interface is now a CDN setting.

In 2000 I wrote the ASP for usetheexperts.com at Web Business Development in Chatsworth, and my friend Lowell did the design. The division of labor was clean. He made the page something a person would trust, and I made the buttons do something. Twenty-six years later the division is the same, except every button now ships with a paragraph of English telling a model what it does, and the model believes the paragraph.

The persuasion is moving too. The tricks that used to live in the pixels, the pre-checked box, the fake countdown timer, the form that asks for more than it needs, are moving into descriptions and schemas, where only a model reads them. The draft’s authors wrote the example themselves. A dress search only needs a size and a price ceiling. Their malicious version asks for age, pregnancy status, location, height, skin tone and purchase history too, with a reasonable-sounding justification attached to each, and a helpful agent answers from whatever it knows about the user. The site logs every answer and builds the profile it was after. Dark patterns didn’t go away. They got a schema.

The New Attack Surface Is a Paragraph of English

The draft’s security section is unusually candid, and anyone shipping tools should read it before the press releases. It concedes that a malicious site can lie in the hints or leave them out, that natural language resists sanitizing, and that whatever a tool returns can carry injected instructions straight into the model. It walks through a tool named finalizeCart, described as finalizing the cart, whose code places the order, and it admits that “there is no guarantee that a WebMCP tool’s declared intent matches its actual behavior.”

Chrome’s security guidance, published June 9, names two ways an agent gets hijacked through WebMCP. A malicious manifest hides instructions in a tool’s name, description or parameters. Contaminated output smuggles them in through the data a tool returns, whether that’s a product review, a forum post or a support ticket. OpenAI wrote last December, about its own browser agent, that prompt injection is “unlikely to ever be fully ‘solved.’” That’s the company running the hackathon.

A web page doesn’t have one author. It has your code, your platform’s code, your CDN’s injected bridge, your analytics vendor, your chat widget and whatever your tag manager loaded this morning, and any of them can register a tool. In June, researchers at National Yang Ming Chiao Tung University in Taiwan posted arXiv:2606.06387, describing what they call Mid-Session Tool Injection, in which a third-party script registers or swaps tools while the agent is mid-task. Their registration-race attack, which hijacks a tool by winning the race to register it, worked 100 percent of the time against GPT-5.4, Claude Opus 4.6 and Gemini 2.5 Flash. The fair caveat is that they ran it on the MCP-B polyfill in a headless Node.js harness rather than in Chrome’s native implementation, and native behavior may differ. The other caveat is that the attack needs nothing more exotic than a script tag, and you probably can’t name every script your site loads.

WebKit’s reviewers read the same draft and found no consent model and no reversibility model. The readOnlyHint flag is advisory. The declarative toolautosubmit attribute lets an agent submit a form with no human review, and a companion explainer contemplates Service Worker tools that run with no tab open and nobody watching. The most interesting entry in OpenAI’s hackathon wasn’t the floor-plan editor, the night-sky planner or the bouquet designer. It was Mandate, a delegation layer that gives agents temporary, revocable access to selected records. A hackathon team took a swing at the missing piece in ten days. The standard has been in draft for fifteen months.

Your Server Thinks It’s the Customer

The clearest account of where this breaks ran on November 11 in The Hacker News, a contributed piece from Token Security. Token built a browser agent called Rehearsal that answers questions inside Token’s own platform by opening pages, setting filters and filling in forms. Then it noticed the agent broke, by default, all three rules Token gives its customers, which are that agents need their own identities, access that fits the job, and an audit trail that isn’t some human’s. Rehearsal ran in the user’s session, so the server saw the user, because, in Token’s words, “nothing in a session cookie points to who the session driver is.” On WebMCP specifically, Token points out that a tool executes as the user, with everything the user is allowed to do, so the standard doesn’t narrow an agent’s reach by itself. Web Bot Auth, the IETF draft from Cloudflare’s Thibault Meunier and Google’s Sandor Major, lets a site verify which agent sent a request. It says nothing about which person the agent works for, or what it was asked to do.

I build MCP servers in production, and this is the difference between the two protocols that matters most. ShopSnap shipped MCP and UCP support this month, opening its storefronts to AI shopping assistants. Server-side, the agent is a client I can identify. It gets its own credentials, I decide which tools it sees and which rows those tools can touch, and the logs separate what the agent did from what a person did. Those are Token’s three rules, and server-side MCP lets you follow every one of them. WebMCP, as drafted, gives up all three. The tool runs in the page with the shopper’s cookies, and to my server it looks exactly like the shopper clicking. The declarative API even hands the submit handler an agentInvoked flag. That flag lives in the browser. My server never sees it unless my own JavaScript forwards it, and anything my JavaScript can send, somebody else’s JavaScript can forge.

So treat every tool you register as a public API endpoint that a stranger can call while holding your customer’s cookies, because that’s what it is. Before you flip Cloudflare’s switch or accept your platform’s defaults, read every description your site will register. That paragraph is now the most important copy on the site, and someone else may have written it. Start read-only, with search, lookups and availability. Anything consequential, an order or a transfer or an account change, gets consequentialHint and a confirmation enforced on the server, ideally a passkey prompt, because a dialog drawn by the page can be drawn by any script on the page. Shopify’s checkout documentation gets this part right. It tells agent builders to sign requests with Web Bot Auth and still get the buyer’s permission before placing the order, and it says outright that the signature doesn’t grant permission. Put untrustedContentHint on every tool that returns reviews, comments or anything else a stranger wrote. Send a Permissions-Policy: tools=() header on the pages where no agent should ever find a tool, and the browser will enforce it before any script on the page runs. Inventory your third-party scripts. Then ask your SaaS vendors the question Token asks, whether their audit logs can tell an agent from a human.

The agent gets through checkout in 10.3 seconds. Your server will swear the customer did it.
