How to Import Existing Resources to OpenTofu [Tutorial]

Your infrastructure estate probably features infrastructure resources that were created outside of your infrastructure-as-code (IaC) process. Luckily, if you are using OpenTofu, you can easily import these resources by either using the CLI or the import block inside your configuration.

In this article, we will cover what OpenTofu import is and when to use it, how to import a resource using the CLI and the import block, best practices for OpenTofu import, and how to manage imports at scale using Spacelift.

TL;DR

  • OpenTofu import brings existing infrastructure under OpenTofu management by recording it in your state file, without changing the resource.
  • You can import in two ways:
    • The tofu import CLI command handles one resource at a time and writes straight to state, with no preview.
    • An import block is reviewed in tofu plan and executed in tofu apply.
  • Use the import block. It’s the recommended method, supports for_each (OpenTofu 1.7+) and the identity argument (OpenTofu 1.12+), and leaves a record in code.
  • tofu plan -generate-config-out can write resource configuration for you, but it’s experimental and doesn’t work with for_each.
  • Find each resource’s import ID in the “Import” section of its OpenTofu Registry page.

What is OpenTofu import and when to use it?

With OpenTofu import, you bind an infrastructure resource in your provider to an OpenTofu resource. If the import is successful, your state file will contain a record of that object’s attributes, and you’ll be able to manage its lifecycle through OpenTofu, as you would do with any other resource created directly through it.

You will need to use the OpenTofu import whenever infrastructure exists outside of your OpenTofu configuration. Here are the most common use cases:

  • You have created infrastructure manually or with custom scripts.
  • You want to migrate from other tools like CloudFormation, Pulumi, Crossplane, or Azure Bicep.
  • State recovery that occurs through accidental deletes or corruption
  • Splitting the state when you have a large stack, and you need to move objects to smaller configurations
  • Emergency changes performed manually

OpenTofu provides two mechanisms for implementing a resource import:

Using the tofu import CLI command

Using the tofu import CLI command was the original approach, inherited from Terraform. If you use this command with an OpenTofu resource address and an ID from your cloud provider, it will write to your state file immediately. However, you will have not plan, preview, or approval step.

tofu import aws_instance.this i-06bf85ad3b9f…

Using the import block

The import block is a configuration-driven import, and you write it in your OpenTofu configurations. It is evaluated during tofu plan, showing you exactly what will happen, and the import itself happens during tofu apply.

The import block has been available since OpenTofu 1.6. It gained for_each support in OpenTofu 1.7, and it gained the identity argument in OpenTofu 1.12.

Note: The identity argument is useful for resources whose identifier is some sort of compound key.

Prerequisites before importing

Before doing an OpenTofu import, you’ll need to ensure you use an OpenTofu version that supports the capabilities you are looking for in the import.

You will need to set up your provider, a remote backend if you are working in a production setup, and read access to the resources. You must also ensure that the resource type supports import (this information is in the documentation).

How to find the right import ID for your resource

Some resources will be simply imported by their IDs, like an EC2 instance. Others, like an aws_security_group_rule, will be a compound key (in this case, you will need the security group ID, the rule type, protocol, ports, and source, all joined by underscores).

In any case, you should always check the “Import” section of a resource at the bottom of the relevant page in the provider documentation in the OpenTofu registry. For your resources, you can also use the cloud provider CLI to find their actual IDs and other parameters without navigating the console.

Method 1: Importing a resource with the tofu import CLI command

Let’s now review how to use the CLI approach to import a resource in OpenTofu.

Basic syntax

To find out what parameters you can use, you can run:

tofu import --help
Usage: tofu [global options] import [options] ADDR ID

Step-by-step example

Now let’s take a look at an example. For this one, I will create an S3 bucket using the CLI:

aws s3api create-bucket \
  --bucket spacelift-tofu-import-demo-2026 \
  --region eu-west-1 \
  --create-bucket-configuration LocationConstraint=eu-west-1

After the bucket is created successfully, let’s create the OpenTofu configuration that will import this resource:

provider "aws" \{
 region = "eu-west-1"
}

resource "aws_s3_bucket" "my_bucket" \{
 bucket = "spacelift-tofu-import-demo-2026"
}

Now I’ll initialize the configuration with tofu init. Let’s import the resource now:

tofu import aws_s3_bucket.my_bucket spacelift-tofu-import-demo-2026

Limitations of CLI import

  • You have one object per invocation, so if you need to import 50 resources, you will need to run the command 50 times.
  • There is no preview, so this command actually mutates the state directly.
  • There is no configuration generation, so you’ll need to write every resource block manually.
  • There is no record in code, so you won’t know in six months if a resource was imported or created.
  • It aligns poorly with CI/CD pipelines.

Method 2: Importing a resource with an import block

The import block is the recommended way to import a resource. It works perfectly with any kind of resource address, so you can still use modules, counts, and for_each.

Basic syntax

import \{
 to = aws_s3_bucket.my_bucket
 id = "spacelift-tofu-import-demo-2026"
}

The id argument vs the newer identity argument

The id argument and the identity one help you track what object you want to import in OpenTofu. For example, importing the same S3 bucket would look like this:

import \{
 to = aws_s3_bucket.my_bucket
 identity = \{
   bucket = "spacelift-tofu-import-demo-2026"
 }

Generating configuration with -generate-config-out in OpenTofu

You can generate the configuration automatically by leveraging the -generate-config-out parameter. Note that this is currently experimental and does not work for resources that use for_each or count.

tofu plan -generate-config-out=generated_resources.tf

Best practices for OpenTofu import

  • Use import blocks instead of the CLI command.
  • Use remote state for your OpenTofu configurations.
  • Enable state versioning before running tofu import.
  • Import resources in small batches using your CI workflow.
  • Treat generated configuration as a draft.
  • Review imports as you would review any other change.

Frequently asked questions

  • What is the difference between tofu import and the import block?

    The tofu import command imports one resource per run and writes it directly to state with no plan or preview. The import block lives in your configuration, so imports show up in tofu plan, run during tofu apply, support for_each, and can generate configuration.

  • Can OpenTofu generate configuration automatically when importing?

    Yes. Running tofu plan -generate-config-out=<file> with import blocks writes HCL for resources that don’t exist in your configuration yet, but the feature is experimental and its output should be treated as a draft.

  • Does OpenTofu support importing all resources?

    No. Import support depends on whether the provider implements it for that resource type.
