Dogfooding Checks and Workspaces: Hard lessons from 3,000 repos

This is the third and final post in a three-part series discussing how CI is changing in the AI era. Read part one, “Why the future of coding needs instant back-pressure”, and part two, “MicroVMs, Egress MITM, and sealed tokens: Sandboxing untrusted code at scale”.

Whiteboard architectures and clean sandbox primitives are easy to admire in isolation. It’s one thing to say you have fast microVMs and host-side credential proxying; it’s an entirely different beast to put that machinery directly between autonomous agents and production repositories.

At Chainguard, our fleet isn’t generating throwaway prototype code or toy pull requests. We maintain roughly 3,000 minimal container images that provide the foundational security baseline for production workloads around the world. Every single day, upstream packages bump, new Common Vulnerabilities and Exposures (CVEs) are published, and patches must be compiled, tested, and shipped immediately. If our pipeline fails, or if a model hallucinates a passing test suite on a compromised library, the blast radius isn’t an internal staging server — it’s the critical supply chain our customers rely on.

In Part 2, we walked through the low-level infrastructure: microVMs with independent kernels, gVisor-based egress MITM, and lazy virtual filesystems that load multi-gigabyte toolchains in milliseconds.

Here’s what happened when we turned that substrate into an everyday reality: how we dogfooded it to replace PR roundtrips with instant tool-call feedback, how we moved thousands of daily builds off GitHub Actions, how our engineers use it right on their desks, and the blunt, unvarnished lessons that reminded us why building this shit is so hard.

Workspaces on our desks

Our engineers run Claude Code inside microVMs, which can be detached and resumed in seconds. They have the option to run --fresh to fan out Workspaces so agents can try competing approaches at once. Credentials stay safe as these agents are building. When they need an API key, the supervisor injects it via the proxy, so it never enters the guest.

Pre-commit hooks for agents

Our agents finish their loop by calling a submit_result tool.

The workspace suspends and the harness — not the model — runs the validators registered for that agent. If any fail, the submission is rejected and the workspace resumes in seconds with the failure logs in context. The agent can’t leave the loop while the checks are failing.

About two dozen of our production agents gate their submissions this way, with validators ranging from structural checks to real Melange builds and tests inside a microVM. One review agent completes a 35-tool-call run in about four minutes, roughly what a single Continuous Integration (CI) roundtrip used to cost. Our CVE-remediation fleets run at 97 to 98 percent weekly success on this stack.

Taking image builds off GitHub Actions

We maintain about 3,000 container images, and package bumps auto-merge about 99 percent of the time. We used to open a pull request for every bump just to trigger the checks. Now the bump bot builds and tests every affected image in microVMs and pushes straight to main if they pass, falling back to a pull request after five failed retries.

Releases use two steps:

  1. The first builds the image and runs its tests. We treat it as untrusted code, with reduced credentials, and record the digests.
  2. The second rebuilds without tests, using the publish credentials, and publishes only if the digests match.

Code that holds the keys never runs anything we don’t trust.

We rolled this out behind a percentage dial with GitHub Actions as the fallback, so a bad day on the new path never blocked the patch queue. The goal for the end of October: patch images with GitHub Actions down, and Actions turned off at the repository level.

This Shit is Hard

Building systems at this layer means confronting structural friction.

Proving that the checks ran is complex. Offloading workload execution to custom infrastructure is relatively straightforward. Verifying that those checks actually happened is not. When you run everything inside standard CI, trust is implicit because the platform that executes the code also guards the branch. The moment you decouple execution from the merge gate, you need a mechanism to prove that a test wasn’t skipped or fabricated. A merge gate that accepts an external cryptographic attestation has to earn that trust check by check. Every signature must immutably bind the exact commit SHA, the environment configuration, and the tamper-proof test verdict together. If there is a single gap in that chain of custody, the attestation is worthless, and you’re forced right back into re-running the entire suite.

The test/publish boundary has to be structural. The boundary separating test execution from publishing must be enforced structurally at the system level. In GitHub Actions, per-job OIDC provides an identity boundary that prevents an untrusted test run from inheriting the deployment role. When you replace that control plane, you can’t depend on developers remembering to keep publish credentials out of the test environment. We had to enforce this separation by construction: Untrusted build scripts and test suites run in low-privilege microVMs stripped of external publish rights, producing only a recorded digest. A completely separate, isolated release phase then rebuilds without running arbitrary test code. It checks that the digests match byte-for-byte and publishes using dedicated credentials. Any compromised third-party code that executes during testing is blind to secrets.

Sealed environments are hard to debug. The exact isolation mechanisms that make microVMs safe — ephemeral instances, default-deny egress, sealed tokens, and tearing down the machine on the first policy violation — also turn the runtime into a black box when a test behaves unexpectedly. When an agent hits an edge case or a build stalls, engineers need real-time streaming logs, execution traces, and kernel telemetry without poking holes in the security boundary. Observability needed to be a core platform feature from day one.

GitHub is still on our critical path for source, events, and checks. Decoupling our compute from GitHub Actions eliminated our largest and most volatile failure domain, but it didn’t magically remove GitHub from our critical path. Our source repositories, git refs, pull request webhooks, and status checks still live on their platform. Our pipelines still feel the tremors when GitHub’s broader API degrades, webhook deliveries queue up, or git operations time out. However, moving image builds and agent evaluations into our own microVMs gave us control over execution, eliminated runner queues, and shielded our core build loops from Actions control plane outages. But as long as the code lives on GitHub, complete platform independence remains an asymptote. We’ve simply isolated the blast radius to the parts of the stack we can actually fix ourselves.
