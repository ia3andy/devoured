One tenant two hundred times bigger

The lab is sensor readings with the usual lookup tables hanging off them. A site is the tenant, and readings stands in for whichever tenant-scoped table grows fastest in your schema:

CREATE TABLE vendors (id int PRIMARY KEY, name text NOT NULL);
CREATE TABLE models  (id int PRIMARY KEY, vendor_id int NOT NULL REFERENCES vendors, name text NOT NULL);
CREATE TABLE units   (id int PRIMARY KEY, symbol text NOT NULL);
CREATE TABLE sites   (id int PRIMARY KEY, name text NOT NULL);
CREATE TABLE sensors (
    id       int PRIMARY KEY,
    site_id  int NOT NULL REFERENCES sites,
    model_id int NOT NULL REFERENCES models,
    unit_id  int NOT NULL REFERENCES units,
    label    text NOT NULL
);
CREATE TABLE readings (
    id        bigint PRIMARY KEY,
    site_id   int NOT NULL REFERENCES sites,
    sensor_id int NOT NULL REFERENCES sensors,
    taken_at  timestamptz NOT NULL,
    value     double precision NOT NULL
);

CREATE INDEX readings_site_time ON readings (site_id, taken_at);

There are 2,000 sites. Most have about 15 sensors and 1,000 readings over two years, and site 1 has 500 sensors and 200,000 readings. Every multi-tenant table I've worked with has had a site 1. Readings are inserted in random time order, so a week of any site is scattered across the heap, and readings carries site_id as a deliberate denormalization so a site's readings can be found through one index without going through sensors.

The query is a dashboard tile, the 50 highest readings at a site in a time window:

PREPARE top(int, timestamptz, timestamptz) AS
SELECT r.id, r.taken_at, r.value,
       s.label, m.name AS model, v.name AS vendor, u.symbol AS unit
FROM readings r
JOIN sensors s ON s.id = r.sensor_id
JOIN models  m ON m.id = s.model_id
JOIN vendors v ON v.id = m.vendor_id
JOIN units   u ON u.id = s.unit_id
WHERE r.site_id = $1
  AND r.taken_at >= $2 AND r.taken_at < $3
ORDER BY r.value DESC, r.id
LIMIT 50;

No index returns readings in value order, so any plan reads the whole window and sorts it. Plans differ in how much work they put into rows that end up outside the top 50. For a small site that's a handful of rows. For site 1 it's most of the query.

It's a PREPARE because that's how it reaches the server from most applications. The production endpoint went through pgx, which prepares by default (so does the Rails adapter); pgJDBC and psycopg 3 switch to server-side prepared statements after a few executions.

How a prepared statement picks its plan

A prepared statement exists to skip planning on repeat calls. On data like this a plan made without the parameters has to guess them, so PostgreSQL doesn't commit straight away. The first five executions each get a custom plan built with the actual values. From the sixth on it also builds a generic plan, once, with $1..$3 unknown, and choose_custom_plan() in plancache.c switches to it whenever its cost is below the average of the custom plans so far. Each custom plan is charged a little extra in that comparison for the planning it costs.

The dashboard opens on ordinary sites far more often than on site 1, so I ran it for six of them and asked pg_prepared_statements which plans it had used:

SELECT name, generic_plans, custom_plans FROM pg_prepared_statements;
 name | generic_plans | custom_plans
------+---------------+--------------
 top  |             1 |            5

Each ordinary site's custom plan cost about 135 with the planning charge, and the generic plan costs 82. Once the generic plan is in use no new custom plans get built, so the average it's compared against never moves again, and when site 1 arrives it gets the generic plan without being planned at all.

Prepared statements live in one backend, so behind a connection pool each connection makes this choice separately from whichever tenants reached it first. Because pg_prepared_statements is session-local, you can only check those counters from inside one of the app's own pooled connections.

The 82 itself is arithmetic on defaults. For site_id = $1 the planner assumes the average site, 2.2 million rows over 2,000 sites, 1,100 rows. For the taken_at range against two unknowns, clauselist_selectivity falls back to DEFAULT_RANGE_INEQ_SEL, 0.5%. That's 5.5 rows, and six rows through four nested-loop lookups on primary keys is cheap. No parameter reaches that arithmetic, so the window doesn't either.

Seeing the plan production runs

Copying the query from the log, pasting in the values and running EXPLAIN ANALYZE won't show any of this. With literals the planner sees site 1 and a real date range, and you get a custom plan. To get what the application gets, repeat the warm-up: PREPARE, execute it five times with ordinary sites, then EXPLAIN (ANALYZE) EXECUTE top(1, ...). SET plan_cache_mode = force_generic_plan skips the warm-up, and since PostgreSQL 16 EXPLAIN (GENERIC_PLAN) shows the generic plan's estimates without running it.

What the buffer count counts

21,823 looks like a lot for a dashboard tile. It adds up exactly once you know how tall each index is, which pageinspect reads from the metapage:

SELECT c.relname, (bt_metap(c.relname)).level
FROM pg_class c
WHERE c.relname IN ('readings_site_time', 'sensors_pkey', 'models_pkey', 'vendors_pkey', 'units_pkey');
      relname       | level
--------------------+-------
 units_pkey         |     0
 sensors_pkey       |     1
 vendors_pkey       |     0
 models_pkey        |     1
 readings_site_time |     2

A lookup in one of these unique indexes touches level + 1 index pages plus one heap page, 3 for sensors and models and 2 for vendors and units, which is 19,830 across all the lookups. The readings scan is the other 1,993: 11 index pages and 1,982 heap pages for 1,983 rows. The counter only ticks when a scan moves to a different buffer, and only once in this week do two consecutive rows share a heap page.

When the planner sees site 1

Forced to plan site 1 for a week, the planner gets the estimate close (1,888 rows against 1,983) and picks a plan for volume: the bitmap scan over the window, sensors, models and vendors read whole into hash tables, and units, with only 20 distinct keys, behind a Memoize node. Its cost is 6,536 and it takes about 6 ms, a good part of it spent hashing 30,000 sensor rows to use 1,983 of them.

The plan it rejected is faster. With enable_hashjoin and enable_mergejoin off the runner-up shows up: it sorts the window first and joins only the top 50. It costs 6,563, 0.4% more, and runs in about 3 ms, half the time of the plan that beat it.

Moving the LIMIT below the joins

Every fast plan above picked the top 50 from readings before joining anything. The query can ask for that order directly, which is usually called a deferred join:

PREPARE top_late(int, timestamptz, timestamptz) AS
SELECT r.id, r.taken_at, r.value,
       s.label, m.name AS model, v.name AS vendor, u.symbol AS unit
FROM (
    SELECT id, sensor_id, taken_at, value
    FROM readings
    WHERE site_id = $1
      AND taken_at >= $2 AND taken_at < $3
    ORDER BY value DESC, id
    LIMIT 50
) r
JOIN sensors s ON s.id = r.sensor_id
JOIN models  m ON m.id = s.model_id
JOIN vendors v ON v.id = m.vendor_id
JOIN units   u ON u.id = s.unit_id
ORDER BY r.value DESC, r.id;

A subquery with a LIMIT isn't pulled up into the outer join (is_simple_subquery() in prepjointree.c refuses it), so the planner can't flatten it back into the original. The outer ORDER BY needs no second sort as long as the joins are nested loops, which keep the subquery's order.

original 5.9 / 11.7 5.7 / 16.8 4.0 / 10.9 24 / 43

deferred join, covering index 0.4 / 0.8 0.4 / 0.8 1.1 / 2.0 1.1 / 1.6

The covering index has a price. It's 123 MB, against 66 MB for readings_site_time and 126 MB for the table, and every new reading writes its value, sensor and id into it, plus the WAL. With the same leading columns it can replace readings_site_time, which makes the difference 57 MB.
