Coding agents are opening more pull requests than ever, and each one waits on CI before anyone can review or merge it. Most CI systems run the entire workflow on every push, even a one-line change. The more your agents push, the more time you spend waiting on CI.

Today, we're announcing Vercel CI in Beta. It runs only the tasks affected by your code change, and spins up only the compute those checks need, the same way Fluid compute scales with your traffic.

At Vercel, our CI now keeps up with our coding agents. Time from git push to "CI passed" is 2-6x faster than it was before.

How it works

Vercel CI uses Turborepo to understand your tasks and which ones depend on each other. It reads turbo.json, so if you're already using Turborepo, there's no separate CI config to write.

If you're not on Turborepo yet, add turbo.json and the turbo package. It works in single-package repos too.

Then tag the tasks you want Vercel CI to run.

\{
  "tasks": \{
    "lint": \{
      "tags": ["ci"]
    }
  }
}

"tags": ["ci"] is all you need to get started. No workflow YAML to maintain, no drift between your CI config and turbo.json, and Remote Cache is on by default.

When you or your agent push code, Vercel CI determines which tasks need to run based on the change. Tasks whose inputs haven't changed come from cache. The remaining tasks each run on their own machine, powered by Hive, Vercel's compute layer, and start as soon as their dependencies finish.

Vercel CI gives each task the compute it needs and nothing more.

Running your CI on Vercel

To get started, follow the documentation or prompt your agent from your repo:

Set up Vercel CI for this repository. Run `npx skills use vercel/ci@setup` and follow the skill's instructions to select initial tasks, configure Vercel CI, and open a pull request.

Once set up, you or your agent can watch and inspect CI through the Vercel dashboard, Vercel CLI, or Vercel MCP. When something fails, go straight to the failing task, see what's blocked behind it, and open its logs, or search across recent runs to see whether a test has been flaky all week.

vc ci ls # List CI runs for the repository
vc ci inspect <run> # List tasks for a run
vc ci logs <run> # Get logs for all tasks in a run
vc ci logs <run> --task web#test --level=error # Get stderr for a specific task
vc ci grep "WARNING" # Search across run logs for a string

Vercel CI posts a check to your pull request on GitHub, so your existing branch protection rules can block merges on failure, the same way they do today.
