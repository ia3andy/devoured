Engineering at DuckDuckGo has just adopted a shared AI coding harness. It can take a piece of work, make a plan, write the code, check what it built in the running app, and open a pull request with evidence attached. Code review is moving towards agents too.

I’m a Design Engineer, and watching this come together has made me think quite differently about the work on my side of the process. If engineering can take on and complete more work in the same amount of time, we need a better way to get good work ready for it. That includes understanding the problem, exploring directions, making decisions, and explaining those decisions clearly enough that someone else can build on them.

We ship apps across iOS, Android, macOS, Windows, and the web. A proposal that sounds straightforward in a task can turn into quite a few design questions once you look at how it needs to work across those platforms. The pace of implementation doesn’t make those questions go away. It makes the time we take to answer them more visible.

The constraint moved

We already have several pieces of an AI-assisted design workflow. A Claude project can turn research into hypotheses and scoped proposals. There’s a home-grown exploration workspace that can read a task, simulate screens across platforms, and export strings and change logs. And there’s early work on automated design review, where agents build UI using the design system and their output is checked against tokens and specs.

Different people built those pieces in different places, each to deal with a real part of the work. I like that. It means we’re not starting from a diagram of an ideal process and waiting for someone to build the whole thing before we learn anything.

But each piece has reached the point where it needs something from the others. A person still reads a task in Asana and carries the context between stages. The exploration workspace can export to the clipboard, but that leaves someone responsible for deciding what to copy, where to put it, and whether the next person has the current version. Engineering’s harness can build and check code, but it doesn’t know about our design system.

Each step can look impressively fast on its own. Put them together and we still have a lot of waiting, interpretation, and manual transfer between them. As engineering gets faster, that transfer starts to look less like an incidental bit of admin and more like part of the work we need to design.

There’s a temptation to describe the answer as “design needs to speed up”. I think we need to be more precise. Speeding through an exploration only helps if we can make a sound decision about it, record the important parts, and give the people implementing it enough context to recognise when something has gone wrong. Otherwise we’re just producing more things for engineering to interpret.

Everyone built the useful bit in front of them

One thing I keep noticing is how reasonable each local decision has been. If you’re building an exploration tool, copying strings to the clipboard is a perfectly understandable way to get them out. If you’re trying to help an agent use a design system, writing down the relevant tokens in Markdown can be a quick way to make the information available. If your tool generates its own JSON, using that file saves you from waiting for another integration.

Then somebody else needs to consume the result and the differences become expensive. We now have design tokens represented in Figma variables, hand-written Markdown, and a tool’s generated JSON. Each has a reason to exist. I can’t ask an agent to check a screen against “the tokens” until we decide which values it should trust, how those values reach the check, and who is responsible when they disagree.

The same applies to a design decision. A task in Asana might explain the problem. A Claude project might contain a useful hypothesis. The exploration workspace might show a direction across five platforms. Those things are related, but the relationship currently depends on a person knowing where to look.

A small contract between stages

The direction I want to try is for each stage to leave a small machine-readable artifact behind. For the design stage, that could be a design spec containing the chosen direction, reference screenshots, the strings, and the tokens used.

It needs enough information for the next stage to act, while staying small enough that somebody can understand and maintain it. If the chosen direction changes, the artifact needs to change with it. If a string or token is missing, I’d rather that was visible than have the coding agent quietly fill in the gap and carry on as though the decision had already been made.

I’m deliberately calling this a design spec rather than a complete description of the product. The exploration workspace simulates screens to communicate intent. That can help us decide whether an approach is worth pursuing across platforms, but it isn’t automatically a pixel-exact source of truth for the native implementation. A simulation may express a relationship that needs a different control or layout on another platform.

Put the check where the work happens

Engineering’s harness already finds checks by naming convention. That gives us a useful seam: a design check can be discovered in the same way as the checks engineering already runs, without changing the harness itself.

I’d like the same check to run twice. First, the coding agent runs it during its own loop and fixes the obvious issues it can identify. Then it runs again in CI as an independent gate, so the result isn’t based solely on what the agent chose to report while it was working. If the result falls below an agreed score threshold, the work gets flagged for a designer to review.

There are a lot of decisions hidden inside that fairly neat description. What does the score measure? Which differences can we check reliably across platforms? What happens when a design file is out of date, or a token value is wrong? A low score might reveal a real implementation problem, but it could also reveal a problem with the reference or the check itself.

I don’t want a number to become a substitute for looking at the work. At the beginning, I’d use the threshold to bring a person into the conversation and compare what the check reported with what the interface actually does. That gives us a way to learn where the check helps and where it needs to improve before we rely on it more heavily.

Who gets to drive?

We’ve talked about designers becoming conductors of these tools, and I understand the appeal. A designer can shape the exploration, make the decisions that hold the experience together, and direct agents towards a result that serves the product.

But I don’t want that to become a rule that every idea has to pass through a designer before anyone can explore it. Product managers and engineers have useful questions too. If the tools help them make an idea concrete enough to discuss, that could make the conversation better.

The difficult part is working out what people can do independently and where the team needs a shared decision. Someone should be able to explore a direction without that exploration quietly becoming an approved design spec. Some integrations are also blocked by organisational permissions, so we need to establish what access is actually required. Equally, a designer needs to be able to change a direction without leaving engineering working from an older artifact that looks authoritative.

The tools will keep moving

Part of what makes this difficult is that the tools change monthly. A convention that seems sensible when one person builds an experiment may be awkward a few weeks later when another system needs to consume its output. Yesterday’s clever setup becomes integration debt, and the person who understood why it worked might also be the only person maintaining it.

I don’t want to stop people experimenting until we’ve agreed on every interface. We need those experiments to find out what’s useful. But once a tool becomes a dependency for other teams, we need to know who can maintain it, how a change is communicated, and what happens if its original builder is unavailable.

The same goes for design files. A check can only be as dependable as the reference it’s checking against. If the file is incomplete or no longer reflects the chosen direction, automating the comparison may just help us find the wrong answer faster. Part of adopting automated review is being honest about which files are ready to support it.

I’m still working through how much of this we should automate before the process has earned that trust. I’d rather connect a small number of stages, inspect what passes between them, and learn from the places where someone needs to intervene. We can add more automation once we understand those decisions well enough to support them.

If your team is building similar tools, I’d start by following one piece of work across the whole path. Find the point where someone copies information, translates a decision, or goes looking for the current token value. Ask what the next person or agent needs to know, and who can keep that information accurate. Then make that handoff explicit before adding another tool to the chain.
