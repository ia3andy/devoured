One of the best ways to measure how well an agent researches and reasons is to give it a question from the past and compare its answer with what happened. For that test to be fair, the agent can only see what was available at the time.

Today we're launching Time Machine for the Perplexity Search API and Context API to let developers and agents show the web as it was on a chosen date. This limits searching and full-page reading to stored copies of the web captured at or before a chosen timestamp.

The live web always knows how things turned out. Ask an agent today what was known before an election or an earnings call, and it will find pages that already report the result. Time Machine lets an agent work on a question as it stood in the past, and lets developers score its answer against what happened next.

That score shows how well the agent researches and forecasts, and whether a new model, prompt, or retrieval setup improved it.

How Time Machine works

Each time Perplexity crawls a page, it saves a copy along with the time it was saved. Over time, every URL builds up a version history, and Time Machine answers from that history instead of the live web.

Add snapshot_as_of to a request and it becomes a cutoff, up to 365 days back today, and that history keeps growing. On search, retrieval only considers pages that were published or first crawled by the cutoff. Each candidate is swapped for its latest copy saved at or before the cutoff and ranking scores the query against that older text. A page that was later updated with the outcome can't rank for it, and its title, date and snippet come from the same copy.

A typical workflow searches first and then reads the pages it finds, so the same cutoff applies to both steps:

  • Search API: Returns pages ranked as described above, with each result's title, date and snippet taken from its copy at the cutoff.
  • Context API: Returns the full text of each page's copy at the cutoff. The live site is never contacted.

Ways teams use Time Machine

The same point-in-time web works for any workflow where hindsight would invalidate the result:

  • Reinforcement learning: Train agents on past questions without the answer leaking into search results, so the reward measures reasoning rather than lookup. See the example below.
  • Forecasting and prediction markets: Replay resolved questions at several points before resolution and score a forecaster's predictions against real outcomes.
  • Finance backtests: Test web-derived signals and research agents with a cutoff hours before earnings calls, FOMC announcements, or acquisitions.
  • Reproducible evaluations: Pin a benchmark to one snapshot_as_of so score changes reflect the model, not new content on the web.
  • Agent replay and debugging: Rerun a past agent session against the web as it was that day, to tell whether a bad answer came from the model or from what the web said at the time.
  • Historical page checks: Read the same URL at two timestamps to see what a pricing page, terms of service, or changelog said on each date, for audits and disputes.

Example: Training a forecasting agent

We used reinforcement learning (RL) to train GLM-5.3 Flash to forecast real political events from 2026 listed on Polymarket.

Each Polymarket question asks about a future event, such as whether a candidate will win an election. The model’s job is to estimate the chances as of the day the question was asked. In the Time Machine run, GLM-5.3 Flash can search news and polls available by that day, but not later coverage announcing the winner. Its forecast might be: “The candidate has an 80% chance of winning.”

The actual result is used to grade the forecast. If the candidate wins, an 80% forecast earns a higher score than a 50% forecast. If the candidate loses, the 80% forecast earns a lower score. That score is the reward. Reinforcement learning uses rewards from many questions to adjust how the model makes future forecasts.

These questions are about events that have already happened. A model searching the live web today can find an article that reports the result. Looking up the winner can earn a high score, but it doesn’t help the model predict who will win the next election. Time Machine sets snapshot_as_of to the date the question was asked, so search can return the polls available by then, but not a later article naming the winner.

Without a cutoff, the model can simply look up the answer. Before any training, it scores 0.94 on held-out questions with the live web and 0.77 with Time Machine. The market scores 0.79 (the Polymarket price on the day each question was asked, scored the same way).

To see how web search affects forecasting, we trained the model twice, once with the live web and once with Time Machine, and scored both on the same held-out questions with Time Machine on, as in real use.

With the live web, every forecast finds the answer and scores the same, so about 90% of training groups have zero gradient and teach the model nothing; with Time Machine only about 25% do, and held-out reward rises from 0.77 to 0.80, above the market.

Time Machine vs Exa Snapshot

We compared Time Machine and Exa Snapshot on three sets of 1,000 queries each: a random sample of Time Machine queries, news queries, and queries from prediction-market research. We ran the same queries on both services, using the same cutoff for each query.

First, we checked how often each service returned a publication date with the page. Time Machine included a date on 98.8% to 99.5% of returned pages across the three sets, compared with 66.1% to 77.7% for Exa.

A publication date alone doesn’t show whether the cutoff held. An article published before an election, for example, can be updated afterward to name the winner. To check for later information, an automated judge read every returned page and flagged any that showed content from after the query’s cutoff.

The judge flagged fewer than 0.5% of Time Machine pages in each set, a lower rate than Exa in all three. The largest gap was on the random sample: 0.25% of Time Machine pages were flagged, compared with 1.10% of Exa pages. Across those 1,000 queries, 18 returned at least one flagged page with Time Machine, compared with 62 with Exa. The gaps were smaller on news and prediction-market queries.

Getting started

Time Machine doesn’t require a new endpoint or setup. Add snapshot_as_of to a Search API or Context API request you already make, and the response reflects the web as it was at that time. Leave it out and the same request returns today's web.

Search API

Search the web as it stood at the cutoff. This query searches python.org with a cutoff of October 20, 2026, so each result's title and snippet come from the page's stored copy for that time, not from today's page.

from perplexity import Perplexity
client = Perplexity()
search = client.search.create(
    query="Latest Python 3 Release on the Python Source Releases page",
    snapshot_as_of="2026-10-20T00:00:00Z",
    search_domain_filter=["python.org"],
    max_results=5,
)
for result in search.results:
    print(result.title, result.url)

Context API

Read a known page as it was at the cutoff. Here the Python Source Releases page lists Python 3.15.0 as the latest release, not the newer version on today's page.

from perplexity import Perplexity
client = Perplexity()
response = client.context.create(
    urls=["https://www.python.org/downloads/source/"],
    snapshot_as_of="2026-10-20T00:00:00Z",
)
page = response.results[0]
if page.status.type == "ok":
    print(page.markdown[:300])
