Where Agents Meet the Browser: Building a Browser-Native Agent

Disconnected Workflows Across Browser Tabs

Ask an engineer, a marketing manager, or a program manager where their day is spent, and the answer is often in a browser: an issue tracker in one tab, a wiki in another, a chat thread, a spreadsheet, an internal dashboard, and a code review. Each tool does its own job well. The friction sits in the work between them, such as reading a long incident thread to write up a ticket, copying numbers from a dashboard into a status doc, or carrying a task across three tools without losing the context that started it. This work is manual, repetitive, and easy to get subtly wrong, and it sits with nearly every role, not only engineers.

Chat-based AI assistants can speed up the work inside a conversation, but not the work between tools. A chat assistant can draft the ticket, but only after someone pastes the thread in, and someone still has to carry the draft back out to the tracker. The person becomes the clipboard, and we set out to change that.

The natural next step is an AI agent that can connect these workflows directly in the browser. But the challenge is more than moving information between tabs. The agent needs to gather the context scattered across tools and turn it into accurate actions, even when those tools offer limited programmatic access. It needs to work within the user’s existing authenticated environment, without making them recreate their workspace. And because that workspace may contain sensitive information, from internal dashboards to unreleased plans, secure data handling has to be a requirement from the start.

To address these challenges, we built a browser-native AI assistant that helps people complete workflows across disconnected tools, working alongside them in the browser they already use with enterprise data-handling requirements in mind.

From Chat Thread to Issue Ticket

Creating a follow-up ticket from an incident thread is a familiar example of this disconnect: the discussion happens in one tool, but the action needs to happen in another.

An engineer must reconstruct the root cause, identify the agreed follow-ups, and carry that context into the issue tracker. The work involves more than copying text—it means separating decisions from suggestions and preserving enough evidence for someone else to act.

With the assistant, the engineer opens its side panel alongside the thread and asks:

The agent reads the discussion and its replies, organizes the findings, and creates the ticket. It returns a link to the result, with supporting references so the engineer can check the summary against the original conversation. Progress appears in the side panel as the agent works.

Instead of manually gathering, reformatting, and transferring information between tools, the engineer gives one request and reviews the result. The workflow connects the discussion to its next action without making the person carry every piece of context between them.

This blog walks through the design decisions that support such workflow: why the agent lives in the browser, how that choice sets its security and data boundaries, how it reads pages built for people, why it isn't tied to a single model, and how tool-specific playbooks keep it reliable on everyday tools. We close with lessons from internal use across engineering and non-engineering roles.

Our Browser-Native Approach

We designed the agent as a Chrome extension that operates within the user's existing environment, paired with a reasoning backend that runs locally on their machine.

Under the Hood: Two Layers and One Stream

The system is split into two distinct layers:

  • The browser layer is the Chrome extension. A content script walks the DOM to build a structured snapshot of the page, and the extension's service worker carries out actions in the tab. Notably, reading and acting go through different mechanisms: the content script reads the DOM, while input (clicks, typing, key presses, hovers) is dispatched through Chrome's debugger protocol.
  • The reasoning layer is a lightweight local FastAPI backend running an agent SDK. It holds the conversation, decides which browser action to take next, and manages session state.

A single turn flows across that boundary like this: the user sends a message from the side panel; the backend starts an agent turn with the browser tools exposed as an in-process tool server; one streaming connection (Server-Sent Events) stays open for the entire turn, across every tool round. When the model calls a browser tool, the backend pushes the request down the stream, the extension executes it in the live tab, and posts the result back, which unblocks the backend and lets the model continue. The agent's output streams token by token over the same connection, so the user watches it work in real time. Sessions data, along with memory and persona, are persisted locally under the user’s control. They survive across machine restarts, or even across different vendor agent harnesses.

Keeping the model-agnostic reasoning layer separate from the browser layer is what lets the same extension run against different harness-and-model backends without changing anything the user sees, a point we'll return to next.

Designing for Enterprise Browser Workflows

Test-automation frameworks have driven browsers over the Chrome DevTools Protocol for years. They are built for CI pipelines, where the browser is disposable, pages are known ahead of time, and sessions are scripted. Our setting was different: the agent had to work in the browser a person already uses, on internal tools, under enterprise data-handling policies. Four requirements shaped the architecture.

  1. Work where the user’s context already exists. People shouldn't have to relaunch their browser with a remote-debugging port, or sign in again through SSO (single sign-on) and MFA (multi-factor authentication), before the agent can help. Running as an extension lets it use the sessions the person already has, without exposing a debugging port.
  2. Control what reaches the reasoning model. An in-browser agent can see internal dashboards, unreleased plans, and code under review. The extension talks only to a lightweight backend on the user's machine that exposes a small, fixed set of routes. The extension redacts sensitive form fields before the page description leaves the browser, and model requests go through approved enterprise model endpoints.
  3. Use structured page information where it is sufficient. Browser use is a narrower problem than general computer control, and vision isn't always needed. The agent reads the accessibility tree by default, receives incremental diffs instead of the full page on every turn, and falls back to screenshots only when needed. This keeps token usage low.
  4. Keep browser capabilities independent of the model and harness. Models and agent frameworks evolve faster than enterprise workflows. Separating browser execution from reasoning lets us change the model-and-harness backend without rebuilding the extension or changing the user-facing workflow.

A Deeper Look at Our Design Principles

Security From Where the Agent Runs

An agent operating with live, authenticated sessions requires security as a core architectural component, not an add-on. Our threat model is addressed through several layers:

  • Local Execution: The local backend only exposes specific routes to the agent, preventing it from being used as a general-purpose web proxy.
  • Domain Scoping: An allowlist restricts navigation to approved sites and helps prevent navigation outside approved sites.
  • Data Redaction: The extension is designed to redact the values of sensitive form fields, such as passwords, payment card numbers, and one-time codes, from the page description before it is sent to the model.
  • Injection Protection. The agent is designed to treat page content as untrusted data rather than instructions. A page-content security boundary is our mitigation for a malicious page trying to smuggle in "ignore your previous instructions and do X" which is a real prompt-injection risk unique to agents that read the open web.

On top of these, the side panel shows every click, navigation, and decision as it happens, so the human in the loop (HITL) can see each action as the agent takes it.

Reading a Page Like a Person

Many browser agents treat the screen like a photograph, relying on screenshots and pixel coordinates. While intuitive, this approach is fragile and expensive, as it breaks on layout shifts and consumes significant token bandwidth.

Instead, we use a semantic approach. A custom DOM walker builds a structured snapshot of the accessibility tree. The agent reasons about elements semantically ("the Search button") and acts on stable references. In our tests, we found this method is more robust to UI changes and significantly reduces token costs. Screenshots remain a fallback for visual elements like charts and canvases, but the "default" vision is lean, structured text.

Perception also has to stay cheap turn after turn. A naive agent re-describes the whole page every time it acts, even though almost nothing has changed between clicks. Ours diffs the page instead: after each action it sends only the regions that actually changed, collapsing everything else to a short placeholder like [... 12 lines unchanged]. Combined with streaming, this keeps each turn with small and incremental text updates instead of re-uploading the whole page every round.

These concepts are simple in theory but require significant engineering to make them reliable in practice. We deliberately made the following design choices:

Stable Element References. Every element in a snapshot is assigned a stable ID (e.g., ref=e42 for "the Reply button"). These IDs are monotonic and never reused, ensuring that incremental diffs are safe. If a model saw a reference last turn, it can trust it still points to the same element this turn, even if the surrounding DOM has shifted.

CDP for Reliable Input. While we read via the accessibility tree, we dispatch input via the Chrome DevTools Protocol. Synthetic DOM events often fail to trigger complex UI behaviors; CDP provides "trusted" input that mirrors human interaction. Although this requires attaching a debugger to the tab, it is a contained cost that ensures reliability without requiring the security risks of an exposed remote port.

Model flexibility and Vendor Independence

We intentionally decoupled the browser layer from the reasoning model. The state of the art in LLMs shifts rapidly; consequently, the enterprise tools built on them should not have to be rebuilt every time a new model is released.

Because of this separation, the extension remains consistent regardless of the backend. We can A/B test different providers, migrate to fine-tuned models, or failover during outages with minimal disruption. This avoids vendor lock-in and transforms model upgrades from "migration projects" into "standing capabilities."

Making it Work Across Real-World Tools

While generalist models provide a powerful foundation, a significant gap exists between their generic capabilities and the specific demands of enterprise environments. Enterprise UIs are notoriously complex: chat applications often obscure context within virtualized lists, issue trackers bury critical actions inside nested modals, and rich-text editors present significant hurdles for structured programmatic input.

To bridge this gap, we developed a system of Application-Specific Playbooks. These strategies act as an intelligent overlay that teaches the agent how to navigate the specific nuances of professional tools with precision:

  • Chat Intelligence: We employ specialized heuristics to traverse virtualized message lists and expand threaded conversations, ensuring the agent captures the complete dialogue history rather than just the visible surface.
  • Productivity Workflows: We optimize for deep-linking and structured data injection, enabling the agent to create documents and spreadsheets with high fidelity, bypassing the fragility of UI-based input.
  • Issue & Task Management: The agent favors direct REST API interaction over brittle UI automation, which provides the speed and reliability necessary for enterprise ticketing systems.
  • Visual Synthesis: We implement custom logic to translate complex system architectures, data flows, and processes into structured diagrams, turning conceptual descriptions into visual documentation.

How People Are Using It at LinkedIn

Since the internal launch, people in engineering and non-engineering roles have used the assistant to bring information together and carry work across tools. Tasks range from investigating an alert to preparing material for a team review. Smaller requests fit between those activities: identifying messages that need a reply, catching up on a discussion, or finding open tickets that have gone without an update. The common starting point is the work already open in the browser: a person asks for help with a specific task, and the assistant works alongside them in that context.

From an Oncall Alert to a Reviewable Handoff

An on-call investigation often begins with a message, but the evidence is scattered across the linked dashboards, logs, and deployment history. The engineer has to connect what fired, when it happened, and what changed around the same time before deciding what to do next. In this workflow, the engineer opens the alert and its replies and asks the assistant to investigate, follow the evidence links, and report its findings without changing anything or posting a response.

The requested result is a timeline, the affected service and environment, a likely cause, and links to the supporting evidence. The engineer checks the diagnosis and can ask the assistant to revisit a conclusion that does not fit the evidence. If the next step involves code, the assistant can carry those findings into a draft task for a coding agent, preserving the evidence links and stopping before submission so the engineer can review it.

Otherwise, it can draft a suggested reply for the engineer to post. The workflow connects investigation to the next action while keeping the decision and final submission with the person—not treating a proposed diagnosis as a confirmed cause.

From Long Documents and Discussions to Team-Review Material

Preparing a team review is another kind of cross-tool work. A long document may contain the information people need, but turning it into a discussion requires selecting the key points, preserving the decisions and numbers, and making unresolved questions visible. Someone coordinating the review can ask the assistant to turn that document into a short slide deck, with one idea per slide and a diagram where it explains a relationship better than text. The deck opens in a new browser tab for review and revision.

The same pattern applies to a discussion with many replies and no obvious outcome. The assistant can summarize the problem, the options people proposed, what was decided, and the remaining questions in a visual explanation. The person compares the result with the source and asks for corrections—for example, checking that an owner or date is supported by the discussion rather than inferred. Follow-up requests in the same session retain the context, allowing the person to refine the material without supplying the document again. This is a planning and communication workflow relevant beyond engineering: the output is not merely a shorter answer, but material people can inspect, revise, and bring into their next conversation.

Keeping a Project’s Context From Week to Week

Program management rarely fits in one sitting. A technical program manager might spend Monday sorting out a dependency between two teams, Wednesday chasing the owner of a blocked ticket, and Friday writing the weekly status update. The browser has the latest tickets, threads and meeting notes. It doesn't keep what ties them together: what was decided, why a date moved, and what still needs follow-up. In a typical chat session, that history is gone once the conversation ends, so the next session starts with the program manager explaining the project again.

To keep that context, the program manager can start a project with the assistant. At the end of a working session, they ask it to record what happened and what to follow up on next week. The assistant suggests what to save, such as a decision, a new risk or an open question, and doesn't write anything until the person approves it. The notes are stored as readable files on the person's own machine. They can also be opened as a mind map that shows how decisions, risks and open items relate.

The next week, the program manager can open a new conversation and ask, "What's the state of the project?" or "What did we decide about the launch date?" The assistant answers from the saved notes, so the program manager doesn't have to explain the background again. When it's time for the weekly update, the assistant can combine those notes with the current ticket status in the issue tracker. The draft then covers both what changed this week and the earlier decisions behind it.

Lessons Learned

Remembering Earlier Work

Users reported that the agent forgot earlier conversations, forcing them to repeat background information before it could help with a new task. That feedback led us to build cross-session memory as well as agentic search to use them.

We made that memory inspectable by storing retained context in plain, human-readable files that users can open, correct, or delete, and view as a live tree or mind map. The agent asks for confirmation before saving changes.

Making Technical Explanations Easier to Follow

Users sometimes struggled to digest long, technical explanations. The information was there, but understanding how the parts connected still took work. We added visual explanations so the assistant could show system relationships, workflows, and data flows alongside the text.

Checking That the Work Was Done

Some failures were easy to overlook because the answer sounded reasonable. A thread summary could look complete even when the agent had missed messages or replies. Handling that request correctly required knowing how the application exposed its history, not just knowing how to summarize text.

Those misses helped shape our application-specific playbooks, which guide the agent through the reading and writing methods that work for each tool.

Helping People Know When to Use it

People didn’t always know which tasks to bring to the assistant, even when it already supported them. Hands-on sessions helped: users tried it on their own work, checked the results, and asked follow-up questions.

Conclusion

We began with the manual work between browser tabs, but building this assistant taught us to look beyond automation: an agent needs to fit into how people gather information, make decisions, and check their work—not simply operate the tools in front of them.
