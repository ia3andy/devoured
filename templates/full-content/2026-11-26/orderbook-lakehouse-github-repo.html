orderbook-lakehouse

A small local data lakehouse for market order-book events. Synthetic exchange events go through a bronze → silver → gold pipeline and end up as tables you can run trading analytics on. It's Scala/Spark on Apache Iceberg, with the infrastructure running in Docker.

For a step-by-step walkthrough of the demo, see GUIDE.md.

The stack

Producer (make generate) ──HTTP──► Redpanda Connect 4.113 (:4195)
                                      │  NDJSON files → s3://orderbook-warehouse/landing/raw_events/
                                      ▼
Spark job (Scala 2.13, local mode) ◄──┘  reads landed files, writes Iceberg tables
   │  Iceberg REST protocol: catalog + metadata
   ▼
Apache Polaris 1.8.0 (:8181) ──► Postgres 17   ── catalog state (persists across restarts)
   │  S3 API
   ▼
SeaweedFS 4.48 (:8333)        ── S3-compatible storage, bucket orderbook-warehouse

  • docker-compose.yml starts the stack (docker compose up -d). Every image is pinned to a version. Startup order:

    Service Purpose
    seaweedfs weed mini all-in-one: S3 API on :8333, admin UI on :23646. Creates the orderbook-warehouse bucket and the admin/password S3 identity on startup
    postgres Polaris metastore. infra/postgres/init.sql creates polaris_schema on first init
    polaris-bootstrap One-off: Polaris admin tool creates the realm and the root/s3cr3t principal in Postgres. Idempotent
    polaris Iceberg REST catalog + management API on :8181, health on :8182
    polaris-init One-off: infra/polaris/setup.sh creates the orderbook catalog and grants. Idempotent (409 = already exists)
    redpanda-connect The only way data comes in: accepts events over HTTP on :4195 and lands them in S3

    docker compose down keeps the data and the catalog; docker compose down -v wipes both together, so they never get out of sync.

  • PolarisSpark.scala builds the shared SparkSession. Spark asks Polaris for table metadata but reads and writes data files directly in SeaweedFS. Endpoints and credentials come from environment variables (POLARIS_*, S3_ENDPOINT, S3_ACCESS_KEY, S3_SECRET_KEY; see .env.example), with defaults that match the compose stack.

  • Makefile has shortcuts for checking Polaris (make catalogs, make tables NAMESPACE=bronze) and for running each job (make help lists them).

The data

The feed has five event types: add, cancel, modify, trade and snapshot. Each event has instrument, timestamp, side, price, qty and seq_no. GenerateSyntheticEvents (make generate) makes realistic demo data and POSTs it to Redpanda Connect, the same way any other producer would. It runs a small matching engine for each instrument. Orders that cross the book trade against resting orders (best price first), market orders hit the best bid or ask, and cancels remove orders that actually exist, so the book gold rebuilds is never crossed. Events are 1s apart by default (GEN_INTERVAL), so 5000 events cover about 80 minutes of one-minute bars. It doesn't emit modify, because gold can't apply one without an order_id. The same seed always gives the same data.

The pipeline

Layer Job What it does
Bronze bronze.raw_events IngestRawEvents Reads the NDJSON files Redpanda Connect landed in S3 with a Structured Streaming query (Trigger.AvailableNow: process what's new, commit, stop). Its checkpoint records which files it has read, so a rerun only picks up new files. Every column is nullable: a value that won't parse becomes null for silver to reject, instead of failing the run. Each row keeps its _source_file and _ingested_at.
Silver silver.book_events BuildSilverEvents Drops malformed rows, removes duplicates on (instrument, seq_no), adds event_date, then MERGE INTOs silver, so a rerun never inserts the same event twice. It stops before writing if more than 50% of a batch is malformed. Partitioned by instrument and date.
Gold BuildGoldAggregates Builds 1-minute OHLCV bars (open/high/low/close/volume) from trades, and top-of-book snapshots (best bid and ask each minute) by keeping a running quantity for every price level. Each run recomputes the minutes its new data touches and MERGEs them in by (instrument, window_start), so reruns and minutes split across runs never duplicate a row. The running book is saved in gold.book_state, so orders from earlier runs still count.

From scratch: make setup && make generate && make pipeline (make pipeline runs ingest, silver and gold in one JVM and Spark session; make ingest, make silver, make gold run them one at a time). make setup (re)creates every table empty and deletes the landed files and the ingest checkpoint (make clear-landing), so it also resets the pipeline on a running stack.

Make runs each job with target/run.sh, a plain java launch on the project's classpath that sbt launcher writes. Make rebuilds it when the sources change, so sbt starts once instead of once per job.

The Scala packages under src/main/scala/orderbook/ follow the same layers:

Package Contents
common PolarisSpark (Spark session wired to Polaris + SeaweedFS), OrderBookSchema, Watermark
bronze / silver / gold Each layer's Create*Table(s) job and the job that writes it
analytics Read-only query jobs
ops CreateNamespaces, MaintainTables, ClearLanding, SmokeTest, ListCatalogs
tools GenerateSyntheticEvents

Tests mirror the same packages under src/test/scala/orderbook/. PipelineIntegrationSpec runs the real jobs end to end against a local Iceberg catalog in a temp directory (no Docker) and checks that incremental runs equal a full recompute, reruns commit nothing, duplicates and malformed events are absorbed, a gold run that crashes midway is recovered, and maintenance doesn't force a full re-read. Run everything with make test.

Ingest (Redpanda Connect)

Events only come in over HTTP. The redpanda-connect service (infra/redpanda-connect/landing.yaml) accepts them and writes them to s3://orderbook-warehouse/landing/raw_events/ as newline-delimited JSON files, one file per batch (up to 5000 events or 5s). make ingest then runs IngestRawEvents against that prefix (STREAM_LANDING) to append the new files to bronze. Bronze loading is micro-batch: events land continuously, and each make ingest moves what has landed into Iceberg.

make generate                    # POSTs the first 5000 synthetic events of the feed
make generate-next               # POSTs the next 5000: new seq_no, later timestamps
make demo-dedup                  # re-sends the last batch, then ingest + silver: all skipped
make snapshots TABLE=silver.book_events   # snapshot history + watermark, from Polaris
make pointers                    # each table's metadata.json pointer, from Postgres
curl --data-binary '\{"event_type":"add","instrument":"BTC-USD","timestamp":"2026-10-26T10:00:00Z","side":"buy","price":100.5,"qty":3,"seq_no":1}' \
  http://localhost:4195/events   # or send your own
make ingest && make silver && make gold

A request body can hold one event or many, one per line. The request returns once the events are written to S3. Lines that aren't valid JSON go to landing/rejected/ instead. Valid JSON with bad values still reaches bronze, as nulls, and silver drops the row. Delivery is at least once; silver's dedupe on (instrument, seq_no) removes any duplicates.

Design points

  • Incremental processing (Watermark.scala): each job records the last upstream Iceberg snapshot ID it processed in the summary of its own output commit, so the data and the watermark are committed together or not at all. The next run reads only the changes since then, using start-snapshot-id, instead of rescanning everything.
  • Idempotent writes: silver's insert-only MERGE skips events already there; gold's MERGEs replace recomputed minutes; gold.book_state, the one output that can't be recomputed safely, is written last, in the commit that carries gold's watermark. A crash at any point is fixed by rerunning.
  • Exact arithmetic: prices and quantities are DECIMAL(18,8), so a price level that's fully cancelled nets to exactly zero and is dropped from the book.
  • Maintenance (MaintainTables): runs Iceberg's data-file and manifest compaction, snapshot expiry and orphan-file cleanup on every table, with configurable retention. Its rewrite commits carry the watermarks forward and record which snapshot they rewrote, so expiring old snapshots doesn't force the next run into a full re-read.
  • Known limitation, documented in the code: modify events aren't counted in the book because the schema has no order_id.

Analytics

Standalone query jobs, each answering one trading question:

  • Spread and cost: SpreadOverTime, EffectiveVsQuotedSpread, VwapVsClose
  • Volatility: RealizedVolatility (rolling standard deviation of log returns), ParkinsonVolatility (based on each bar's high/low range)
  • Microstructure signals: BookImbalanceVsNextBar (does bid/ask imbalance predict the next bar's direction?), LiquidityDryUpWindows, TradeThroughDetection
  • Surveillance: CancelToAddRatio, a classic warning sign for spoofing or quote-stuffing

Several of these join trades against the snapshot from the previous minute, so the results are approximate.

Other things to know

  • It's a demo setup, not production. Credentials are hardcoded, and there's no STS.
  • Tests (munit, sbt test) cover the transform functions (clean, ohlcvBars, topOfBookSnapshots, conform). Those functions don't do any I/O, so they're tested on small in-memory DataFrames.
  • No scheduler is set up yet; you run jobs by hand or with an external cron.

Setup notes

  1. stsUnavailable: true on the catalog's storageConfigInfo (infra/polaris/setup.sh). SeaweedFS has no STS, so Polaris doesn't try to hand out scoped credentials, and Spark uses the S3 keys directly.
  2. Two S3 endpoints on the catalog. Polaris returns the catalog's endpoint to clients, and it takes precedence over the client's own s3.endpoint. Spark runs on the host, so endpoint is http://localhost:8333. Polaris also writes each new metadata.json itself, from inside the Compose network, so endpointInternal is http://seaweedfs:8333.
  3. S3A for remove_orphan_files. That maintenance procedure lists files through Hadoop's FileSystem API rather than S3FileIO, so PolarisSpark also registers S3AFileSystem (hadoop-aws) for the s3:// scheme against the same endpoint.
  4. Polaris + Postgres. Polaris doesn't create its database schema (infra/postgres/init.sql does), and with JDBC storage the realm and root principal come from the admin tool's bootstrap command, not from POLARIS_BOOTSTRAP_CREDENTIALS. Keep apache/polaris and apache/polaris-admin-tool on the same version when upgrading.
