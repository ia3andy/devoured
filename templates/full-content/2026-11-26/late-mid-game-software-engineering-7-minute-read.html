Late Mid-Game Software Engineering

In the past month, I’ve had many discussions with folks about how their work is changing due to AI. My sense is that it is increasingly confusing how to allocate one’s time. Simultaneously, I’ve been reflecting that my own work now feels like the “late mid-game” of Factorio, where the automation is really starting to kick off, and you’re spending more time on the meta game of copy/pasting automation.

There is still a significant capabilities and diffusion overhang in software engineering. As a result, there is so much more that can be done now that could not have been done a year ago. However, the field is also lacking good conceptual handles for what the work of a modern (post-modern? post-agent?) software engineer entails. As of the past few weeks, the “software factory” model is having its moment of memetic virality. While this is one useful concept for post-agent software work, it is not a full description of where we’re going.

Where we are going is, well, in my opinion quite exciting. I’ve never had more fun at work, despite all the change and disruption. I now roughly categorize work into these buckets:

RTS-style agent management

Individual agents, agent teams/factories, and – soon – agent swarms. This is the most straightforward replacement for “coding time” and maker-time work.

People often label this as “you’re now the manager of a team of agents!” While there’s something directionally correct about this, this is not my preferred analogy. In my head, it’s closer to “you’re now the tech lead (TL) of a team of agents”:

  • Managers: Leadership (up/down the chain) alignment.
  • TLs: Ranking of problems, exploring other work to do.

On one level, you act as a TL of a set of agents. Increasingly, though, the prudent course of action is to further uplevel yourself into a TL of a workstream, where you only periodically check-in without your input, with agents working nearly fully autonomously on your behalf.

This “high APM” RTS-style agent management is therefore partly transitional, and we’re clearly moving towards a more “fully lights out” future.

High-stakes technical work

This bucket is technical work which we have not yet made amenable to agents. There’s a moving frontier of what this high-stakes technical work actually means. This is work like:

  • Deep review of long-term-impacting decisions (e.g., is $THING safe to roll out now).
  • Deep review of code (e.g., “this critical piece of code that – yes, we’ve had 10 agents review – but my team will have a Bad Day if any bit of this goes wrong so I do need to spend actual human cycles making sure this is completely correct and aligned”). Code review is already becoming more quadruple-checking the things that the agent verified versus doing the actual verification yourself.
  • Auditing system usage and making adjustments when necessary. Auditing system usage has gone from needing to look manually at graphs to do the work, to mostly being spot checks.
  • Operations work. Rolling things out, monitoring, sanity checks, validation. This category is increasingly being handed off to agents, and is a fantastic opportunity for reducing human toil and increasing shipping velocity.

As agents improve in their technical ability, this bucket looks less like “sit down in a sealed room and write a document” and more like: converse with agents, guide decisions, provide bits of input to nudge things in a sane direction. But it’s still more brain-engaging than the RTS bucket, in that you need to be single-threadedly thinking about the problem at hand.

People/org work

Software engineering still, of course, has a rich interpersonal component to it. If anything, having low-friction people/org alignment “done right” has become more important with agents, since there’s much more knowledge work happening and team/org/project state change happens much more quickly.

Concretely, the time gets spent on:

  • Aligning people with projects, transferring context between people, setting direction.
  • Talking up/down leadership chains; translating context for up/down leadership chains.
  • Evangelizing work; pushing for new systems to exist; pushing for processes to change.
  • Mentoring, career development, feedback.
  • Alignment on timelines. This is increasingly hard now, given agents make things bimodal of either “way faster than we’d previously planned for” or “wicked hard problems we can’t throw agents at, so the timeline is mostly a shrugging emoji on a post-it note”.

Agentable work you’re still doing

Technical work which is able to be done by the RTS/Factorio agent swarm which you are still doing yourself. Here be dragons.

There is still some benefit to exposing yourself to code-level tasks, but if you are spending more than an hour or two a week in things which are in the “agentable” bucket (distinct from the “high-stakes technical work” bucket), then this is a dangerous place to be spending time. This also applies to work where you’re still instructing agents in a single-threaded fashion for cases when you could automate your inputs away.

It’s easy to spend too much time in this bucket. I think this is the primary failure mode of many engineers. There’s an illusion of productivity which prevents you from doing the meta-level thinking of upleveling yourself.

Meta/exploratory work

Technical or organizational work which does not fall into the preceding buckets, but is counterintuitively often the highest-leverage work that you can do.

This type of work is more difficult to schedule. It requires a mixture of deep focus, creativity, and openness to change. In this bucket I include things like: removing old processes that are not providing value anymore; adding new processes that allow agents to go further without human involvement; playing with prototypes to explore a design space; pushing agents farther than you thought possible to see where they break; working on personal tools to make yourself incrementally more productive or incrementally less cognitively overloaded.

This bucket benefits highly from ambition. It also benefits from a network of colleagues who are all individually trying to raise their ambition, with whom you can share new ideas/techniques/discoveries.

Over the past months, I’ve been attempting to balance my time to be able to spend as much time as possible in the meta/exploratory work, people/org work, and high-stakes technical work. Meta/exploratory work is high-payoff because it allows you to reduce the amount of time you need to spend in RTS-style agent management (via further levels of automation) and in high-stakes technical work (by shaving off pieces of it to no longer require focused attention). Much of the high-stakes technical work has also been transitioning to be meta/exploratory work over the course of the past year.

There is a growing, but jagged, frontier of work that can be fully black-box automated – similar to technical escape velocity. So far, the work that seems resistant to being sucked into the agentable black box is non-verifiable targets like UX, security properties, system intent, system boundaries, whether to accept inbound feature requests, seeing the forest for the trees, principal-agent problems, coordination problems, and so on.

Once you have a reasonably verifiable target – even if it is only fuzzily verifiable – then the work to get to that target largely falls to agent teams/swarms/factories. Yet, it is not simply the case that humans can find solace in “we get to do the fuzzy unverifiable work”; agents qualitatively make progress on that, too, with each model generation. Agents’ ability to do problem selection, intent and taste are also improving. So there’s a continuous rediscovery of what pieces require human input, and what can be fully given over.
