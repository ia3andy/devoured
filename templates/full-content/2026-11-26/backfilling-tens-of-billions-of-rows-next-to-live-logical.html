Backfilling Tens of Billions of Rows Next to Live Logical Replication (Part 2)

How a resumable parallel backfill, two disk-pressure incidents and a second look at the reconciliation query got tens of billions of rows across, with logical replication running the whole time.

Key Takeaways

  • A parallel backfill has to be stoppable. ID-range segments with per-batch checkpoints let workers be restarted, added or removed mid-run without copying a row twice or skipping one. An even split by ID is not an even split by rows.
  • Bulk loading into a node whose WAL archiving is failing fills the disk with WAL. The safe recovery is to mark as archived only the WAL files proven to be in the backup repository, never to delete WAL by hand.
  • One very large source transaction can stall a subscription and pin WAL on the source. Switching the subscription to streaming = parallel drained the backlog without restarting anything.
  • The reconciliation pass from Part 1 had two flaws that only show at scale: it missed updates that changed only the Information column, and the planner chose a join that would read hundreds of times more rows than needed. Both are fixed, and the corrected query is below.

This is Part 2 of a migration series.

Where We Are

All three large tables are now fully backfilled on the target, and the migration is days from cutover. When Part 1 was written the parent table was still being copied; since then parent_table, child_table and child_table_2 have all landed, together holding tens of billions of rows.

The plan held. The execution taught us things the plan could not. This part covers what broke at that scale, how each problem was handled without restarting the production cluster, and what we would do differently next time.

A Backfill You Can Stop

The backfill had to survive being stopped, restarted and re-sized in production, so every design choice served that. A single COPY stream would have taken weeks, so each large table was copied by several workers in parallel, each owning its own range of IDs.

The upper bound was fixed before anything started. The subscription was created with copy_data = false, and the lowest ID the subscription wrote on the target, minus one, became the backfill’s MAX_ID. Everything above that line is replication’s job; everything at or below it is the backfill’s. That one number is also the dividing line the monitor in Part 1 checks on each side.

How the script works:

  1. On start, it reads how far each previous segment got and works out exactly which ID ranges are still missing.
  2. It splits only those missing ranges evenly across the configured number of workers and saves that plan atomically.
  3. Each worker copies its range in batches of 10 million IDs. One batch is one COPY from source to target, so a batch either lands whole or rolls back.
  4. After each batch commits, the worker records the last ID it finished in a checkpoint file named after its own segment. No other segment can ever read it.
  5. On restart, a quick count on both sides catches the rare batch that committed just before its checkpoint was saved, so it is marked done instead of copied twice.

The Stuck Worker

One morning a single worker had produced no log line for seven hours while the others moved on. On the source, its session showed state = active with wait_event = ClientRead: the server was waiting on a client that had stopped reading. A network stall had silently broken the stream.

Because the batch in flight was one transaction, the fix was safe: stop the script, let that batch roll back, start again. The script re-split what was left, and the stalled range was copied again from its last checkpoint. We added TCP keepalives to the connection strings afterwards so a dead peer is noticed in minutes, not hours.

Even IDs, uneven work

The workers did not finish together. Some finished well ahead of the others. The split was even in IDs, not in actual rows. ID ranges are not uniformly dense: gaps from rolled-back inserts, deleted rows and changes in write volume over the years mean two equal ID ranges can hold very different row counts.

The Indexes You Keep During a Bulk Load

Every index on a table is written again for every row a COPY inserts. For a load of billions of rows, the textbook approach is to load into a table with only the indexes the load itself needs, then build the rest afterwards in one sorted pass.

Index Keep during the load? Why
Primary key Yes Logical replication finds rows by it for every UPDATE and DELETE it applies.
An index leading on ID Yes The restart check and the exact per-batch counts are range lookups on ID.
Secondary and unique indexes No Nothing reads them during the load. Rebuild them before cutover.

Incident: WAL Grew to Tens of Terabytes on the Target

Partway through the backfill, the target’s data volume reached 95%, and almost all of it was pg_wal. The backfill’s COPY streams and the replication apply were generating WAL quickly, which is expected. What was not expected was that none of it was being removed.

Why WAL piles up

PostgreSQL only recycles a WAL segment once two things are true: a checkpoint has passed it, and, when archiving is on, the archiver has reported it safely archived. Each segment waiting for the archiver has a .ready marker in pg_wal/archive_status; a successful archive renames it to .done.

The safe recovery

  1. Ask the backup tool for the newest WAL segment it holds, and spot-check that segment by actually restoring it with archive-get.
  2. List the WAL segments genuinely present in the repository.
  3. Intersect that list with the .ready markers on the target.
  4. For segments in both lists only, rename .ready to .done. No WAL file is touched; only the marker changes.
  5. Run CHECKPOINT. PostgreSQL removes the now-archived segments on its own.

Incident: Replication Lag Filling the Source

Later in the backfill the pressure moved to the source. Two subscriptions had fallen behind, and their replication slots were holding WAL on the source primary.

By default a subscription applies a transaction only after it has committed on the source. The source decodes the whole transaction first, spilling it to disk once it outgrows logical_decoding_work_mem, then sends it, and a single apply worker replays it.

Small Things That Would Have Broken Cutover

A timezone mismatch hiding in a column default

The source cluster ran in a regional, non-UTC timezone. The new cluster ran in UTC. Several tables use timestamp without time zone columns with DEFAULT now(). After cutover, every new row would have been stamped hours apart from every historical row. The fix was to set the target’s TimeZone to match the source on every node.

A subscription that has failed quietly

The subscription for audit_table showed as enabled, but the table-sync worker had been failing. The replication role had never been granted SELECT on that one table. Check srsubstate in pg_subscription_rel reaches r (ready) for every table.

Revisiting the Reconciliation From Part 1

Flaw 1: it compared the wrong column

The trigger captures a row when Information or Timestamp changes. The reconciliation only applied rows where Timestamp differed. The fix is to compare both columns.

Flaw 2: the plan read far more than it wrote

For this statement the right plan is a nested loop: walk the audit rows in the batch, and look up each matching child_table row by primary key. Turning off hash and merge joins for the batch session forces it.

The corrected statement

SET enable_hashjoin = off;
SET enable_mergejoin = off;

UPDATE "child_table" td
SET "Information" = tu."Information"->'Information',
    "Timestamp"   = tu."child_table_Timestamp"
FROM "audit_table" tu
WHERE td."ID" = tu."ID"
  AND td."ID" <= :backfill_max_id
  AND tu."Information"->'Information' IS NOT NULL
  AND (td."Timestamp"   IS DISTINCT FROM tu."child_table_Timestamp"
       OR td."Information" IS DISTINCT FROM tu."Information"->'Information')
  AND tu."ID" BETWEEN :batch_start AND :batch_end;

Verifying Without COUNT(*)

At tens of billions of rows, an exact COUNT(*) is hours of full scans. We built confidence in layers:

  • reltuples and n_live_tup estimates.
  • MIN("ID") and MAX("ID") validation.
  • Rows copied, summed from the backfill’s own per-batch log.
  • Exact counts on randomly chosen ID windows.

Closing Thought

The pattern that worked every time was the same: find out what the database is actually doing before changing anything, prefer the change that can be undone, and refuse the shortcut that trades a visible problem for an invisible one.
